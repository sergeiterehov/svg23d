# 0039. Кэш готовых деталей и прогресс сборки по этапам

- **Статус:** Accepted
- **Дата:** 2026-11-05
- **Связано:** [ADR-0010](0010-worker-protocol.md), [ADR-0030](0030-curve-quality-at-import.md)

## Контекст

Сборка модели — самая долгая операция после импорта. Замер на `samples/name.svg` (14 листьев,
34 тыс. треугольников, допуск 0.02 мм):

| Этап                             | Время   |
| -------------------------------- | ------- |
| 2D-сечения листьев               | 30 мс   |
| Призмы (`extrude`)               | 22 мс   |
| **Вырезание гнёзд (`subtract`)** | 1150 мс |
| Склейка деталей и меш            | 3 мс    |

То есть 97 % времени — булевы вычитания «призрак вышестоящего листа из другой детали» из каждого
нижестоящего листа (до 91 операции на модель). При этом любая правка (высота, допуск, порядок,
цвет) пересобирала всё заново, а статус-бар показывал только «Построение модели…» без прогресса:
протокол `{type:'progress', stage, ratio}` существовал, но воркер всегда слал одну стадию, а
`geometryClient` эти сообщения игнорировал.

## Рассмотренные варианты

1. **Кэшировать 2D-сечения.** Дёшево и безопасно, но сечение — это 2.5 % времени сборки: выигрыш
   не заметен.
2. **Кэшировать тела листьев (после вырезания гнёзд).** Пропускает как раз дорогую часть, но
   `manifold-3d` не даёт `clone()`, а `unionSolids` и `meshFromSolid` потребляют входные объекты —
   пришлось бы вручную управлять временем жизни WASM-объектов между заданиями воркера.
3. **Кэшировать готовые детали как меши** (наш выбор). `PartMesh` — обычные типизированные массивы:
   их можно хранить между заданиями, копировать и передавать в основной поток без владения
   ресурсами. Ключ считается по всему, от чего зависит деталь.

## Решение

### Кэш

- `buildModel` принимает необязательные `cache: BuildCache` и `onProgress`. Ядро не хранит
  состояние: владельцем кэша выступает воркер (`Map` с LRU на 64 детали).
- Ключ детали — `язык | partId | свои листья | режущие листья`:
  - **свои листья** — сигнатура каждого: хеш контуров, `fillRule`, маска, источники объединения,
    `zFrom/zTo`, фаски, флаг «скрыт»; **допуск в ключ своего тела не входит** — он принадлежит
    призраку, который лист вырезает в нижних деталях;
  - **режущие листья** — те, что по правилам ADR-0004/0005 действительно режут эту деталь (другая
    деталь, выше по порядку, с пересечением по Z и bbox); их сигнатура дополняется допуском;
  - **язык** — потому что предупреждения внутри детали локализованы (ADR-0037).
- Контуры хешируются двумя независимыми потоками FNV-1a по координатам с квантованием 1e-6 мм:
  коллизия практически исключена, а стоимость хеша (~0.2 мс) на два порядка ниже сборки.
- Кэш хранит **свои копии** мешей: наружу уходят исходные массивы, которые воркер передаёт
  в основной поток трансфером. На попадании возвращается ещё одна копия.
- Имя и цвет детали в ключ не входят: они подставляются при выдаче, чтобы смена цвета не
  пересобирала геометрию.
- Меш для вида (`displayParts`) тоже кэшируется; в записи он `undefined` (совпадает с основным),
  `null` (все листья скрыты — деталь не рисуется) или отдельный меш без скрытых листьев.

### Прогресс

- Стадии: `sections` → `prisms` → `merge` с весами 0.35 / 0.60 / 0.05. Сообщение несёт **id
  стадии**, а не готовую строку: перевод живёт в интерфейсе (`status.stage.*`).
- Воркер шлёт прогресс не чаще, чем раз в 40 мс, и только при смене стадии, шаге ≥ 2 % или раз
  в 250 мс; финальные 100 % отправляются всегда. Поток воркера при этом занят, но сообщения
  доходят до основного сразу — React успевает перерисовать статус-бар.
- Статус-бар показывает «Сечения · 35 %» вместо безликого «Построение модели…».

## Последствия

- Правка одного элемента пересобирает только зависимые детали: в тесте «плита + штифт» смена
  высоты плиты пересобирает одну деталь из двух, а смена допуска штифта — только плиту
  (гнездо), сам штифт берётся из кэша.
- Исправления, меняющие геометрию листа, инвалидируют его деталь и все детали, которые он режет;
  смена цвета и скрытие — нет (скрытие меняет только меш для вида, но ключ включает флаг, чтобы
  не путать записи).
- Память ограничена: 64 детали (несколько мегабайт), самые старые вытесняются; кэш живёт в
  воркере до перезагрузки страницы.
- Тесты: `tests/buildCache.test.ts` — переиспользование без изменений, точечная инвалидация,
  зависимость гнезда от допуска режущего листа, цвет вне ключа, скрытая деталь не попадает в
  набор для вида, монотонный прогресс со стадиями и 100 % на полностью кэшированной сборке.
